# v1.5.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** KoNeko v1.5.0 — (1) chain cards show node names even when the chain references nodes in another group; (2) long-press a group tab on the home group bar opens that group's edit screen.

**Architecture:** (1) In `ConfigurationAdapter.rebuildChainDisplayCache()`, collect the node IDs referenced by chains that are missing from the current group's in-memory name map, resolve them with ONE batched `ProfileManager.getProfiles(missingIds)` DB lookup, merge the names into the map, then resolve chain display strings as before — scrolling still reads memory only. (2) In the `TabLayoutMediator` tab-configuration lambda, replace the no-op long-click consumer with a listener that launches `GroupSettingsActivity` with `EXTRA_GROUP_ID` for the long-pressed tab's group, using `tab.position` at click time so a stale captured position can never open the wrong group.

**Tech Stack:** Kotlin, Android (TabLayout / TabLayoutMediator), Room (ProfileManager), existing KoNeko unit-test style (pure-function tests + file-parsing tests in `app/src/test/java/io/nekohasekai/sagernet/ui/`).

**Spec:** User-confirmed 2026-11-18: (1) same-group chain nodes already show (v1.4.44); cross-group nodes show nothing — fix it. (2) Long-press a group tab on the home group bar → that group's edit screen. Versioning: user picked option 2 (SemVer from now on) — this release has new features, so it is v1.5.0 (minor bump); bug-fix-only releases go to patch. No other changes.

## Review Focus

- A chain referencing a node that was deleted after the chain was built: the deleted ID is missing from both the in-memory map and the DB lookup, so it is skipped exactly like before — the chain shows only its surviving nodes, never a blank or a crash.
- A chain referencing a node in a group the user later deletes: same as above — skipped, no crash.
- Rebuild runs on the main thread in `onAdd`/`onUpdated`/`onRemoved`/delete paths (inside `configurationListView.post { }`): the batched lookup must stay a single query over only the missing IDs, so a rebuild with no cross-group nodes does zero DB work.
- Long-press on a tab after groups were added/removed/reordered: the listener must resolve the group at click time from `tab.position`, not from a position captured when the tab was configured.
- Long-press must not break the existing single-tap tab switch or the press-scale animation, and must still consume the event (return true) so the long-press toast stays suppressed.

- [ ] **Step 7: Implement the batched cross-group resolution in `rebuildChainDisplayCache()`**

Current body builds `nameById` as an immutable map from `configurationList` and resolves chains. Change it to:

```kotlin
fun rebuildChainDisplayCache() {
    chainDisplayCache.clear()
    val nameById = configurationList.mapValues { it.value.displayName() }.toMutableMap()
    val chainProxies = configurationList.values
        .filter { it.type == ProxyEntity.TYPE_CHAIN }
        .mapNotNull { it.chainBean?.proxies }
    val missingIds = collectMissingChainNodeIds(chainProxies, nameById)
    if (missingIds.isNotEmpty()) {
        for (profile in ProfileManager.getProfiles(missingIds.toList())) {
            nameById[profile.id] = profile.displayName()
        }
    }
    for ((id, profile) in configurationList) {
        if (profile.type == ProxyEntity.TYPE_CHAIN) {
            val proxies = profile.chainBean?.proxies ?: continue
            chainDisplayCache[id] = resolveChainDisplayNames(proxies, nameById)
        }
    }
}
```

Keep every existing call site (`reloadProfiles`, `onAdd`, `onUpdated`, `onRemoved`, the two fragment delete paths) unchanged — they already call `rebuildChainDisplayCache()`. `ProfileManager` is already imported in this file (used by `getItem`); add the import if the compiler says it is missing.
