### Task 5 findings (verified against the code, 2026-11-16)

**Confirmed mechanism.** `RawUpdater.doUpdate` (`RawUpdater.kt:63-73`) tries direct first (`executeSubscriptionRequest(..., useProxy = false)`), and only when the service is Connected retries via the local mixed inbound (`useProxy = true`). The direct failure is only logged (`Logs.i("subscription direct fetch failed, retrying via proxy: ...")`); the error the user sees is the proxy attempt's EOF — the direct reason is swallowed, exactly as suspected.

The direct attempt is NOT tunnel-free. `executeSubscriptionRequest` with `useProxy=false` builds a client with only `tryH3Direct()` (`RawUpdater.kt:229-242`); Go `Execute()` then calls `doH3Direct()` (`libcore/http.go:212-213`), which races two attempts:
- ECH HTTPS: `http.Client` whose `DialTLSContext` uses a bare `var d net.Dialer` (`http.go:249-258`) — no `Control` hook, no custom `Resolver`. (The ECH config itself is fetched via `gLocalDNSTransport`, the platform local DNS transport from `InitCore`, `nb4a.go:47` — but the data dial is still unprotected.)
- H3/QUIC: `http3.Transport` with the default dialer (`http.go:265-274`) — likewise no protect hook, no custom resolver.

`http.go` contains no `Control`, `Protect`, or `AutoDetectInterfaceControl` call at all. The protect path exists only for the box service: `BoxInstance.SetAsMain()` → `goServeProtect(true)` (`box.go:189, 243-252`) serves a Unix socket `protect_path` under `<cache>/../no_backup`, forwarding fds to `intfBox.AutoDetectInterfaceControl(fd)` (the main process's `VpnService.protect()`). The HTTP client never uses it. So "direct" in `doH3Direct` means only "not via the SOCKS5 mixed inbound" — the sockets are still captured by the TUN, and Go's default resolver reads the system DNS, which under VPN is the tunnel's DNS (sing-box local DNS).

That explains the user's control test exactly, given their DNS settings (`enableDnsRouting=true`, `remoteDns=https://dns.google/dns-query`, `directDns=https://223.5.5.5/dns-query`, `enableFakeDns=true`):
- CN (`jkun.1qqdg.cn`): sing-box DNS routing sends the query to direct DNS (223.5.5.5, direct outbound) → real IP; the dial enters the TUN but sing-box routing (geoip:cn bypass) sends it out the direct outbound → works even with a dead node.
- Non-CN (`234.qzz.io`, `clash.theconsole.top`): the query goes to remote DNS (dns.google DoH via the proxy outbound) or fake DNS → dead node → resolution fails, or a fake-IP dial is routed to the dead proxy → EOF. The proxy retry then fails the same way, and that EOF is what the user sees.
- VPN off: no TUN, system DNS is the real network DNS, dials go straight out → all 4 update.

Note: the v1.4.33 #1181 change (direct-first) was still the right call — it fixed the hang/deadlock. What remains is only that "direct" is not tunnel-free.

**Fix options.**
- **(A) Go-side protect + direct resolver in `libcore/http.go` — RECOMMENDED as the true fix. Needs a libcore rebuild.** In `doH3Direct`, set `net.Dialer.Control` on the ECH dialer and the H3 transport's dialer to pass each new fd to the protect server (same `protect_path` Unix-socket mechanism `goServeProtect` already serves), AND give the dialer a custom `net.Resolver` whose `Dial` opens a protected connection to the direct DNS (223.5.5.5) — protect alone is not enough, the DNS lookup itself must also bypass the tunnel. Open question for implementation: the subscription fetch runs in the bg process, while the protect server is started by the main process (`SetAsMain`); the bg process must be able to reach the shared `protect_path` socket, and a protect failure must fall back to an unprotected dial, not hard-fail. Work: one Go file + rebuild `libcore.aar` + dead-node VPN re-test. Risk: moderate — the dial path serves every subscription fetch.
- **(B) Kotlin-side direct fetch with `SagerNet.underlyingNetwork.openConnection` in `RawUpdater` — no rebuild.** `SagerNet.underlyingNetwork` (pre-VPN `Network`, set by `DefaultNetworkListener`, `SagerNet.kt:86, 207`) already exists for tunnel-free sockets/DNS and is used by `LocalResolverImpl` and `pingTest`. Doing the subscription GET through it bypasses the TUN by construction. Cost: it duplicates the Go client's TLS version/insecure handling and UA logic in Kotlin, and loses H3/ECH/TLS-pinning (plain H1.1/H2 only) — two fetch implementations to maintain. Work: small-to-moderate, Kotlin only.
- **(C) Surface the direct attempt's error — tiny, Kotlin only, diagnosis only.** Keep the direct exception in `doUpdate` and include it in the final error ("direct: …; proxy: …"). No behavior change; the next diagnosis would be immediate. Zero risk, but not a fix.

**Decision needed from the user:** (A) is the true fix but requires a libcore rebuild — do it in the next batch, or take (B)/(C) instead? No code was changed for Task 5 in v1.4.34; subscription behavior is unchanged.
